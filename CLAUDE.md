# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

WrapperForge is a contract-bound multi-agent pipeline that forges idiomatic API client wrappers in
multiple languages from one shared spec. A macro agent drafts a language-agnostic implementation plan
(human-approved), micro agents implement the wrapper per language, and a blind QC harness statically
replays pre-approved test cases — calling the real backend and the wrapper-server side by side and
diffing responses. No wrapper source is ever inspected by the QC step.

The full design (locked decisions, rationale, phase-by-phase history) lives in `doc/plan.md` — read it
before making architectural changes; it is the source of truth, more detailed than this file.

## Pipeline stages (in order)

1. **Hand-written contract** — `core/<api-name>/contract.md` (e.g. `core/mock-api/contract.md`). Always
   authored by a human, never generated by any skill. Fixed operation semantics.
2. **`/macro-planning` skill** (`.claude/skills/macro-planning/`) — takes `contract.md` + the API's
   `openapi.json` + a direct-backend base URL, drafts four artifacts into
   `drafts/macro_output/<api-name>/`: `stage_plan.md`, `qc_interface.md`, `qc_interface.openapi.json`,
   `cases.json` (+ optional `language_notes.md`). Runs an unbounded human-approval loop (approval keyword:
   **"approved"**, case-insensitive) before `scripts/promote.py` copies drafts verbatim into
   `core/<api-name>/`. Never touches `contract.md`. Never chains into `/implement-wrapper`.
3. **`/implement-wrapper --language <python|go|javascript>` skill** (`.claude/skills/implement-wrapper/`)
   — reads only from an already-approved `core/<api-name>/` (never `drafts/`), one language per run (run
   3× total for full coverage). Drafts a no-code `wrappers/<api-name>/_plan.<language>.md`, waits for the
   same "approved" gate, then generates `wrappers/<api-name>/<language>/{lib,server}/`, smoke-tests the
   `PORT` + `GET /health` convention, starts the server, and runs `tests/audit.py` against it as its final
   step — QC is automatic per language run, not a separate invocation.
4. **`tests/audit.py`** — static, language-agnostic, pure replay-and-compare. Spawns no processes, seeds
   nothing. Loads `core/<api-name>/cases.json` (fully-resolved `direct`/`wrapper` call specs, no live
   derivation) and `core/<api-name>/qc_interface.openapi.json`, calls both the real backend (already
   running — started manually by the user, out-of-band) and the QC server (already running — started by
   `/implement-wrapper`), and compares responses restricted to fields declared in the OpenAPI response
   schema (schema-driven allowlist; falls back to full-body compare if no schema found). Logs
   pass/fail + free-text reason per case. Exit code 0 iff every case passed.

Directionality is strict and one-way: `core/` is read-only to the wrapper-building stage; `drafts/` is
never read by `/implement-wrapper`; `audit.py` never reads anything under `wrappers/<lang>/` — it only
speaks HTTP against the two base URLs it's given.

## Multi-API namespacing

Every artifact under `core/`, `drafts/macro_output/`, and `wrappers/` is namespaced by an `api-name` slug
derived from the contract file's parent directory (`core/<api-name>/contract.md`), so multiple independent
APIs can coexist (only `mock-api` exists today). See
`.claude/skills/macro-planning/references/directory_conventions.md`.

## Commands

**Mock backend** (the "provider" every wrapper is tested against — FastAPI, in-memory, deterministic
given a `SEED`):
```bash
cd backend/mock_api
python -m venv .venv && .venv/Scripts/pip install -r requirements.txt   # first time (Windows)
SEED=42 uvicorn main:app --reload --port 8000        # bash
$env:SEED=42; uvicorn main:app --reload --port 8000  # PowerShell
```
Must be started manually, out-of-band, before any `/implement-wrapper` run — it is never spawned by any
skill or script. `GET /health` returns `{"status": "ok", "seed": <int>}`.

**Run the QC harness standalone** (normally invoked automatically as step 6 of `/implement-wrapper`):
```bash
python3 tests/audit.py \
  --cases core/<api-name>/cases.json \
  --openapi core/<api-name>/qc_interface.openapi.json \
  --server-base-url http://localhost:<wrapper-server-port> \
  [--direct-base-url http://localhost:8000]   # optional if cases.json has top-level "direct_base_url"
```

**Skill preflight/promotion scripts** (normally run by the skills themselves, not directly by a human):
```bash
python3 .claude/skills/macro-planning/scripts/preflight.py <contract_path> <openapi_path>
python3 .claude/skills/macro-planning/scripts/promote.py <api-name> --repo-root <repo_root>
python3 .claude/skills/implement-wrapper/scripts/preflight.py <api-name> <language> --repo-root <repo_root>
python3 .claude/skills/implement-wrapper/scripts/smoke_test_server.py <port>
```

**Python wrapper venv** — created fresh under `wrappers/<api-name>/python/`, deliberately isolated from
`backend/mock_api/.venv` (separate projects, never share or reuse each other's venv):
```bash
cd wrappers/<api-name>/python
uv venv --python 3.12
uv pip install -r requirements.txt --python .venv
.venv/bin/uvicorn server.main:app --port "$PORT"
```

There is no top-level build/lint/test command for the whole repo — each stage (backend, each language's
wrapper) is its own small project with its own toolchain per the fixed per-language defaults below.

## Fixed per-language defaults (locked — do not re-decide per run)

- **Python:** `requests` for the client library, FastAPI + `uvicorn` for the QC server, typed exceptions
  (e.g. `TaskNotFoundError`) for not-found/invalid-input, a typed result object (not an exception) for
  partial-failure operations.
- **Go:** standard library only (`net/http`, `encoding/json`, `http.ServeMux`) — zero external
  dependencies. Explicit `error` returns, `context.Context` as first client-method argument, a per-item
  error slice for partial-failure operations.
- **JavaScript:** standard library only — global `fetch` for the client, built-in `node:http` for the QC
  server (no Express/Fastify), zero `package.json` dependencies. `async`/`await`, thrown typed `Error`
  subclasses, an `allSettled`-style result object for partial-failure operations.

All three: minimal/no external dependencies, favoring standard library or a single well-known package
over frameworks. Every language's QC server must bind to a `PORT` env var and expose `GET /health` → 200
— this is a non-negotiable process convention, not a per-language choice.

## Conventions that matter across the whole pipeline

- **Approval gate keyword:** both `/macro-planning` and `/implement-wrapper` require the literal word
  "approved" (case-insensitive; close variants like "approve" accepted) before promoting drafts or
  generating code. Enthusiasm without the keyword ("looks great!") is still feedback-mode — ask directly,
  never infer approval.
- **1:1 endpoint mapping (locked):** `qc_interface.md`/`qc_interface.openapi.json` always define one QC
  route per contract operation (`POST /wrapper/create`, `GET /wrapper/get/{id}`, ...), never a uniform
  `/invoke` endpoint. Mirrors real SDK method-per-operation shape and gives REST-semantics coverage
  (status codes) for free.
- **`cases.json` is static and pre-resolved**, authored by `/macro-planning` and approved before
  `/implement-wrapper` or `audit.py` ever run — never derived live, never hand-written under `tests/`.
  Each case has independent `direct` and `wrapper` call specs (not one shared spec against two base URLs),
  so a genuine routing divergence between backend and QC server doesn't silently break the test file.
- **Schema-driven comparison allowlist:** `audit.py` only compares fields declared in the matching
  OpenAPI response schema for that path/method/status; undeclared extras (e.g. request IDs) are ignored.
  A schema behind a `$ref` is treated as unresolved and falls back to full-body comparison — `audit.py`
  deliberately does not resolve `components.schemas` references.
  `priority_score`/`created_at` are the deliberate seeded-random fields that make wrapper divergence
  detectable in that comparison.
- **`bulk_update` is the deliberate friction point:** partial success/failure over multiple items, with at
  least one item designed to fail in every test case touching it. Each language must make an explicit,
  idiomatic choice for representing a part-success/part-failure response — first-pass divergence here is
  expected and acceptable to report honestly, not a bug to hide.
- **No skill ever chains into the next stage automatically.** `/macro-planning` promoting to `core/` does
  not trigger `/implement-wrapper`; running one language's `/implement-wrapper` does not trigger the next
  language. Each invocation is a separate, manual, user-triggered step.
- **Neither server is started/stopped by `audit.py`.** The real backend is started manually by the user
  once, out-of-band. Each language's QC server is started and stopped by that language's own
  `/implement-wrapper` run, around the `audit.py` invocation.
